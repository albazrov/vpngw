# Archived runbook: shell bot security release

> This is a historical runbook for the former shell Telegram bot. Do not use it to deploy, migrate, roll back, or operate the supported release. The current release is Python-only; use [the Python production runbook](python-bot-production.md) and [Python bot guide](../../python_bot/README.md).

## Объём

Release bundle закрывает несколько проблем: использует настроенный `ADG_BIN`, убирает Telegram token из curl argv/environment, проверяет root-only stats directory и удаляет `chmod 777`. Он не включает проверку целевой VPN-локации и не разрешает live reconnect.

## Production inventory и preconditions

Сверять детали с [production inventory](../production-inventory.md). Значения ниже предоставлены оператором и должны быть подтверждены на устройстве перед выкладкой:

- `MAIN_SH_DIR=/usr/local/bin/vpngw`
- `ADG_BIN=/opt/adguardvpn_cli/adguardvpn-cli`
- `VPN_IF=tun0`, `NET_IF=eth0`
- Root cron запускает `adguardvpn-starter.sh` каждую минуту и ещё раз при `@reboot` через 45 секунд.
- Бот `vpn-tg-bot.sh` в crontab отсутствует; он управляется `vpn-tg-bot.service` (`User=root`, `Restart=always`, `RestartSec=10`, `After=network.target`).
- Последний inventory сообщил `root:root 755` для bot script и sourced `vpn-functions.sh`; более ранний snapshot был `pi:pi 755`. Parent-directory permissions и владельцы всех root-cron scripts нужно проверить до release.
- Проверить владельца/mode всего пути, включая `/usr/local/bin/vpngw` и родительские директории. Root-owned файл не защищён, если `pi` может заменить его через writable parent directory.
- Collector в 23:42 обнаружил token в argv до текущего source fix. Оператор должен отозвать старый token в BotFather и заменить его в protected config до старта обновлённого unit. Не печатать token в shell args, journal или report.
- Root cron запускает также starter, bypass updater, hourly report, auth helper и другие scripts. На время обновления требуется согласованное окно: сохранить root crontab, временно отключить только vpngw cron entries и остановить bot unit; не останавливать весь cron daemon.
- `/etc/vpn-gw.conf` и `/etc/msmtprc` имеют `root:root 600` по последнему snapshot; не менять их этой задачей.

**Не выполнять live reconnect в рамках 0.1.** Starter запускается каждую минуту, а бот и starter пока не используют общий lock. Во время ручного reconnect starter может воспринять краткий разрыв как отказ и начать собственное recovery-переключение. Production smoke test, вызывающий `connect`, откладывается до общего lock/окна с согласованным управлением cron или проводится на изолированном тестовом узле.

Не использовать широкий `pkill -f`. Если owner/mode не приведены к безопасным значениям, credential leak не устранён или нет независимого доступа к Pi, production deployment отложить.

## Проверки до выкладки

На машине разработки, из корня репозитория:

```bash
bash -n vpn-functions.sh
bash -n vpn-tg-bot.sh
bash -n vpn-tg-send.sh

bash -n adguardvpn-starter.sh

bash tests/test_adguard_cli.sh

bash tests/test_runtime_directory_permissions.sh
shellcheck vpn-functions.sh vpn-tg-bot.sh vpn-tg-send.sh vpn-bypass-update.sh \
  adguardvpn-starter.sh vpn-hourly-report.sh vpn-auth-helper.sh tests/test_adguard_cli.sh \
  tests/test_telegram_token_argv.sh tests/test_runtime_directory_permissions.sh
```

Последняя команда требует установленного ShellCheck. В среде, где он отсутствует, это ограничение нужно указать в PR и выполнить проверку в CI до merge.

Regression tests проверяют:

- `tests/test_adguard_cli.sh`: fake CLI получает ровно `connect -l <ISO>`; exit code пробрасывается; пустой location и отсутствующий CLI отклоняются;
- `tests/test_telegram_token_argv.sh`: token отсутствует в curl argv и передаётся только через config FD; неизвестный endpoint и неверный token отклоняются;
- `tests/test_runtime_directory_permissions.sh`: принимается только каталог с точными owner/mode; отклоняются mode `777` и symlink.

На Raspberry Pi под доверенной административной учётной записью проверить только требуемые значения, не выводя Telegram token или другие секреты:

```bash
sudo bash -c 'source /etc/vpn-gw.conf; printf "MAIN_SH_DIR=%s\nADG_BIN=%s\n" "$MAIN_SH_DIR" "$ADG_BIN"; command -v "$ADG_BIN"'
```

Проверить, что `ADG_BIN` указывает на ожидаемый исполняемый файл и имеет права на запуск для пользователя бота. Не менять `/etc/vpn-gw.conf` этой задачей.

Проверить file metadata без чтения секретного содержимого:

```bash
sudo stat -c '%U:%G %a %n' /etc/vpn-gw.conf /etc/msmtprc \
  /usr/local/bin/vpngw/vpn-functions.sh /usr/local/bin/vpngw/vpn-tg-bot.sh
sudo namei -l /usr/local/bin/vpngw/vpn-functions.sh /usr/local/bin/vpngw/vpn-tg-bot.sh
```

Записать owner/mode и пользователя процесса в [production inventory](../production-inventory.md), но не копировать значения конфигурации или токены.

## Выкладка на production

Переключение локации может прервать VPN-туннель. Выполнять только в согласованное окно, с доступом вне тестируемого VPN и подтверждённым recovery-путём.

Перед запуском обновлённых scripts установить и применить reviewed tmpfiles rule, чтобы runtime directory существовал до старта systemd/cron и имел mode `0700`. Команды меняют только `/dev/shm/vpn_stats`; не очищают его содержимое:

```bash
SOURCE_DIR="$HOME/app/vpngw"
sudo install -o root -g root -m 0644 \
  "$SOURCE_DIR/deploy/vpngw-tmpfiles.conf.example" \
  /etc/tmpfiles.d/vpngw.conf
sudo systemd-tmpfiles --create /etc/tmpfiles.d/vpngw.conf
sudo stat -c '%U:%G %a %n' /dev/shm/vpn_stats
```

Продолжать только если последняя команда показывает `root:root 700`. Если нет — остановиться и выяснить причину; не запускать unit scripts и не использовать `chmod 777`.

Проверенный code payload SHA задачи 0.1: `1b775b7d7007375424c455a95eb9be532e38ce07`. Более поздние documentation-only commits допустимы только если production files совпадают с этим approved code SHA. Если release PR одобрил другой code SHA, заменить `EXPECTED_CODE_SHA` на его полный SHA. Выполнять блок в одной shell-сессии под пользователем `pi`; он немедленно остановится при любой ошибке.

```bash
set -Eeuo pipefail
SOURCE_DIR="$HOME/app/vpngw"
EXPECTED_CODE_SHA="1b775b7d7007375424c455a95eb9be532e38ce07"
ACTUAL_SHA=$(git -C "$SOURCE_DIR" rev-parse HEAD)
git -C "$SOURCE_DIR" cat-file -e "$EXPECTED_CODE_SHA^{commit}"
if ! git -C "$SOURCE_DIR" merge-base --is-ancestor "$EXPECTED_CODE_SHA" "$ACTUAL_SHA"; then
  printf 'Approved code SHA %s is not an ancestor of checkout %s\n' "$EXPECTED_CODE_SHA" "$ACTUAL_SHA" >&2
  exit 1
fi
if [[ -n "$(git -C "$SOURCE_DIR" status --porcelain)" ]]; then
  printf 'Source checkout is not clean; refusing deployment.\n' >&2
  exit 1
fi
for payload in vpn-functions.sh vpn-tg-bot.sh tests/test_adguard_cli.sh; do
  if ! git -C "$SOURCE_DIR" diff --quiet "$EXPECTED_CODE_SHA" "$ACTUAL_SHA" -- "$payload"; then
    printf 'Deploy payload differs from approved code SHA: %s\n' "$payload" >&2
    exit 1
  fi
done

## Выкладка security bundle

Это обновление меняет несколько scripts, которыми root управляет через systemd и cron. Выполнять в maintenance window с локальным/внеполосным доступом к Pi. Не отправлять reconnect-команды боту.

### Preflight и остановка consumers

1. Выполнить BotFather token rotation и обновить только `TG_TOKEN` в защищённом `/etc/vpn-gw.conf` без вывода значения. Не запускать старую версию после ротации: она снова раскроет новый token в argv.
2. Проверить F-14 для всего каталога: все root-executed scripts, `/usr/local/bin/vpngw` и parent directories должны быть root-owned и non-writable пользователем `pi`. Если проверка не проходит, остановиться.
3. Сохранить root crontab в root-only backup. Через `sudo crontab -e` временно отключить только строки vpngw, не останавливая cron daemon и не затрагивая unrelated jobs. Проверить, что vpngw расписание приостановлено.
4. Остановить bot unit: `sudo systemctl stop vpn-tg-bot.service`. Дождаться завершения уже запущенных vpngw cron jobs; не использовать широкий `pkill -f`.

### Проверенный source payload

Оператору следует подставить полный reviewed SHA security bundle в `EXPECTED_CODE_SHA`. Выполнять preflight в одной shell-сессии под `pi`; блок откажется работать на dirty checkout или если payload files отличаются от approved SHA.

```bash
set -Eeuo pipefail
SOURCE_DIR="$HOME/app/vpngw"
EXPECTED_CODE_SHA='<полный SHA reviewed security bundle>'
ACTIVE_DIR='/usr/local/bin/vpngw'

git -C "$SOURCE_DIR" cat-file -e "$EXPECTED_CODE_SHA^{commit}"

  vpn-hourly-report.sh vpn-tg-bot.sh vpn-tg-send.sh

PAYLOAD_FILES=("${FILES[@]}" deploy/vpngw-tmpfiles.conf.example)
for file in "${PAYLOAD_FILES[@]}"; do

2. Установить все scripts как root-owned и проверить syntax до переключения:

```bash
for file in "${FILES[@]}"; do

  sudo bash -n "$ACTIVE_DIR/$file.new"

```bash

sudo systemctl is-active vpn-tg-bot.service
sudo journalctl -u vpn-tg-bot.service --since '-5 minutes' --no-pager
```

2. Запустить collector. Продолжать только если token argv check=`NO`, stats dir=`root:root 700`, source checkout clean, active payload hashes match source и fake CLI test=`PASS`.
3. Провести безопасные health checks: unit active, `tun0` присутствует, IPv4 forwarding=1; client-routing/connectivity проверить по отдельному согласованному runbook. Не вызывать `/set_*` на production: starter запускается каждую минуту, а общий lock ещё не внедрён.
4. Только после checks восстановить исходный root crontab backup и убедиться, что unrelated jobs сохранены.

### Failure handling

Если код не проходит smoke checks, не восстанавливать автоматически backups, созданные до этого security fix: они содержат token argv leak и/или `chmod 777`. Оставить bot unit остановленным и vpngw cron entries paused, сохранить журналы без secrets и исправить ошибку. Возвращать только ранее проверенный и hardened release. Не запускать live VPN reconnect ради проверки token/runtime fixes.
- `vpn-tg-bot.sh` backup path: взять из report; `NOT FOUND` требует выяснения
- Проверка fake CLI: взять из report; должна быть `PASS`
- Token argv check: должен быть `NO` после credential-safe transport и ротации token
- `/dev/shm/vpn_stats`: должен быть `root:root 700`; cold-start test обязателен
- Production smoke test / причина отложения: заполнить вручную; reconnect запрещён до снятия блокирующих рисков
- Health checks: взять статусы из report и вручную добавить фактический connectivity/client-routing test
- Rollback проверен/не требовался: заполнить вручную; collector не выполняет rollback
- Оператор и дата: взять из report и дополнить фактическим результатом работ

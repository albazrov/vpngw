# Runbook задачи 0.1: вызов настроенного AdGuard CLI

## Объём

Задача исправляет обработчик переключения в `vpn-tg-bot.sh`: используется настроенный `ADG_BIN`, ошибка или отсутствие CLI явно завершают операцию до обновления маршрутов. Не меняются allowlist локаций, проверка фактической страны и production routing logic.

- Путь к исполняемому CLI (`ADG_BIN`): `________________`
- Реальный способ запуска бота (systemd unit, supervisor или иной): `________________`
- Пользователь/группа/права активного `vpn-tg-bot.sh`: `________________`
- Текущая локация и способ ручного восстановления доступа: `________________`
- Ответственный и окно выкладки: `________________`

Не использовать предположительное имя systemd unit и не останавливать процесс через широкий `pkill -f`. Если способ запуска/остановки не установлен или нет ручного доступа к шлюзу, production deployment отложить.

## Проверки до выкладки

На машине разработки, из корня репозитория:

```bash
bash -n vpn-functions.sh
bash -n vpn-tg-bot.sh
bash -n tests/test_adguard_cli.sh
bash tests/test_adguard_cli.sh
shellcheck vpn-functions.sh vpn-tg-bot.sh tests/test_adguard_cli.sh
```

Последняя команда требует установленного ShellCheck. В среде, где он отсутствует, это ограничение нужно указать в PR и выполнить проверку в CI до merge.

Тест `tests/test_adguard_cli.sh` проверяет:

- fake CLI получает ровно `connect -l <ISO>`;
- ненулевой exit code fake CLI передаётся вызывающему коду;
- пустой location и отсутствующий исполняемый путь отклоняются.

На Raspberry Pi под доверенной административной учётной записью проверить только требуемые значения, не выводя Telegram token или другие секреты:

```bash
sudo bash -c 'source /etc/vpn-gw.conf; printf "MAIN_SH_DIR=%s\nADG_BIN=%s\n" "$MAIN_SH_DIR" "$ADG_BIN"; command -v "$ADG_BIN"'
```

Проверить, что `ADG_BIN` указывает на ожидаемый исполняемый файл и имеет права на запуск для пользователя бота. Не менять `/etc/vpn-gw.conf` этой задачей.

## Выкладка на production

Переключение локации может прервать VPN-туннель. Выполнять только в согласованное окно, с доступом вне тестируемого VPN и подтверждённым recovery-путём.

1. Получить commit SHA, прошедший review и необходимые checks. Проверить, что он содержит только ожидаемые изменения задачи 0.1.
2. Подставить фактический `MAIN_SH_DIR`, полученный выше, и проверить активный файл:

```bash
ACTIVE_DIR='<проверенное значение MAIN_SH_DIR>'
ACTIVE="$ACTIVE_DIR/vpn-tg-bot.sh"
sudo test -f "$ACTIVE"
sudo stat -c 'owner=%U group=%G mode=%a path=%n' "$ACTIVE"
```

1. Определить фактический supervisor и штатно остановить только процесс Telegram-бота. Не останавливать `adguardvpn-starter`, routing scripts или VPN CLI daemon.
2. Создать backup текущего файла и подготовить новый рядом с ним (одна файловая система нужна для атомарного rename):

```bash
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
SOURCE='<путь к проверенному vpn-tg-bot.sh из commit SHA>'
BACKUP="$ACTIVE.pre-0.1.$STAMP"
NEW="$ACTIVE.new.$STAMP"
OWNER=$(sudo stat -c '%u' "$ACTIVE")
GROUP=$(sudo stat -c '%g' "$ACTIVE")
MODE=$(sudo stat -c '%a' "$ACTIVE")
sudo cp -a "$ACTIVE" "$BACKUP"
sudo install -o "$OWNER" -g "$GROUP" -m "$MODE" "$SOURCE" "$NEW"
sudo bash -n "$NEW"
sudo mv -f "$NEW" "$ACTIVE"
```

Если проверка нового файла не проходит, не запускать бот: восстановить `BACKUP` и расследовать причину.

1. Запустить бота штатным supervisor. Проверить его статус и журнал. До функционального теста проверить, что основной VPN-интерфейс и forwarding работают.

## Production smoke test

Негативные случаи (missing CLI и ненулевой exit code) проверяются fake CLI в тесте выше; намеренно ломать production `ADG_BIN` или подменять его на fake CLI нельзя.

Для проверки реального пути подключения требуется controlled action. Использовать только если допустим кратковременный reconnect:

1. Записать текущую локацию и убедиться, что есть независимый доступ для восстановления.
2. Через разрешённый private Telegram chat выбрать в меню текущую локацию, если она доступна. Это всё равно переподключение и может кратковременно прервать трафик.
3. Проверить отсутствие ошибки CLI в журнале бота, наличие ожидаемого интерфейса и connectivity, а также сохранность client routing/bypass. Для этой задачи не трактовать одно сообщение бота как доказательство корректной целевой страны: проверка фактической локации относится к задаче 0.2.
4. Если безопасно инициировать reconnect нельзя, ограничиться проверкой запуска бота и тестом fake CLI; записать, что end-to-end production test отложен до изолированного test-сервера. Не проводить рискованный тест только ради закрытия чек-листа.

## Rollback

Откатывать при ошибке старта бота, повторных ошибках `ADG_BIN`, неожиданном разрыве основного туннеля или ухудшении маршрутизации.

1. Штатно остановить только подтверждённый bot supervisor.
2. Восстановить backup атомарной заменой в том же каталоге:

```bash
ROLLBACK_NEW="$ACTIVE.rollback.$STAMP"
sudo cp -a "$BACKUP" "$ROLLBACK_NEW"
sudo mv -f "$ROLLBACK_NEW" "$ACTIVE"
```

1. Запустить bot supervisor, проверить его статус/логи и проверить основной VPN/connectivity/client routing.
2. Не удалять backup до успешного наблюдения и завершения PR review; зафиксировать commit SHA, причину rollback и результаты диагностики.

Rollback этой задачи возвращает только предыдущий файл бота; он не изменяет конфигурацию, VPN-сессию намеренно или маршруты. Если восстановление не возвращает сеть, перейти к документированному recovery-процессу шлюза и не повторять deployment.

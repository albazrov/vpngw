# Runbook задачи 0.1: вызов настроенного AdGuard CLI

## Объём

Задача исправляет обработчик переключения в `vpn-tg-bot.sh`: используется настроенный `ADG_BIN`, ошибка или отсутствие CLI явно завершают операцию до обновления маршрутов. Не меняются allowlist локаций, проверка фактической страны и production routing logic.

## Production inventory и preconditions

Сверять детали с [production inventory](../production-inventory.md). Значения ниже предоставлены оператором и должны быть подтверждены на устройстве перед выкладкой:

- `MAIN_SH_DIR=/usr/local/bin/vpngw`
- `ADG_BIN=/opt/adguardvpn_cli/adguardvpn-cli`
- `VPN_IF=tun0`, `NET_IF=eth0`
- Root cron запускает `adguardvpn-starter.sh` каждую минуту и ещё раз при `@reboot` через 45 секунд.
- Бот `vpn-tg-bot.sh` в crontab отсутствует; он управляется `vpn-tg-bot.service` (`User=root`, `Restart=always`, `RestartSec=10`, `After=network.target`).
- Последний inventory сообщил, что и bot script, и sourced `vpn-functions.sh` принадлежат `pi:pi` (`755`), а root service выполняет их с root privileges. Сначала закрыть F-14; не сохранять этот owner при production deployment.
- Проверить владельца/mode всего пути, включая `/usr/local/bin/vpngw` и родительские директории. Root-owned файл не защищён, если `pi` может заменить его через writable parent directory.
- Последний inventory также обнаружил Telegram token в argv одного процесса. Сначала выполнить задачу 0.0 (отзыв/ротация и устранение argv exposure); до этого не перезапускать production bot и не выкладывать 0.1.
- `/etc/vpn-gw.conf` и `/etc/msmtprc` имеют `root:root 600` по последнему snapshot; не менять их этой задачей.

**Не выполнять live reconnect в рамках 0.1.** Starter запускается каждую минуту, а бот и starter пока не используют общий lock. Во время ручного reconnect starter может воспринять краткий разрыв как отказ и начать собственное recovery-переключение. Production smoke test, вызывающий `connect`, откладывается до общего lock/окна с согласованным управлением cron или проводится на изолированном тестовом узле.

Не использовать широкий `pkill -f`. Если owner/mode не приведены к безопасным значениям, credential leak не устранён или нет независимого доступа к Pi, production deployment отложить.

## Проверки до выкладки

На машине разработки, из корня репозитория:

```bash
bash -n vpn-functions.sh
bash -n vpn-tg-bot.sh
bash -n tests/test_adguard_cli.sh
bash tests/test_adguard_cli.sh
shellcheck vpn-functions.sh vpn-tg-bot.sh tests/test_adguard_cli.sh
```

Последняя команда требует установленного ShellCheck. В среде, где он отсутствует, это ограничение нужно указать в PR и выполнить проверку в CI до merge.

Тест `tests/test_adguard_cli.sh` проверяет:

- fake CLI получает ровно `connect -l <ISO>`;
- ненулевой exit code fake CLI передаётся вызывающему коду;
- пустой location и отсутствующий исполняемый путь отклоняются.

На Raspberry Pi под доверенной административной учётной записью проверить только требуемые значения, не выводя Telegram token или другие секреты:

```bash
sudo bash -c 'source /etc/vpn-gw.conf; printf "MAIN_SH_DIR=%s\nADG_BIN=%s\n" "$MAIN_SH_DIR" "$ADG_BIN"; command -v "$ADG_BIN"'
```

Проверить, что `ADG_BIN` указывает на ожидаемый исполняемый файл и имеет права на запуск для пользователя бота. Не менять `/etc/vpn-gw.conf` этой задачей.

Проверить file metadata без чтения секретного содержимого:

```bash
sudo stat -c '%U:%G %a %n' /etc/vpn-gw.conf /etc/msmtprc \
  /usr/local/bin/vpngw/vpn-functions.sh /usr/local/bin/vpngw/vpn-tg-bot.sh
```

Записать owner/mode и пользователя процесса в [production inventory](../production-inventory.md), но не копировать значения конфигурации или токены.

## Выкладка на production

Переключение локации может прервать VPN-туннель. Выполнять только в согласованное окно, с доступом вне тестируемого VPN и подтверждённым recovery-путём.

Проверенный code payload SHA задачи 0.1: `1b775b7d7007375424c455a95eb9be532e38ce07`. Более поздние documentation-only commits допустимы только если production files совпадают с этим approved code SHA. Если release PR одобрил другой code SHA, заменить `EXPECTED_CODE_SHA` на его полный SHA. Выполнять блок в одной shell-сессии под пользователем `pi`; он немедленно остановится при любой ошибке.

```bash
set -Eeuo pipefail
SOURCE_DIR="$HOME/app/vpngw"
EXPECTED_CODE_SHA="1b775b7d7007375424c455a95eb9be532e38ce07"
ACTUAL_SHA=$(git -C "$SOURCE_DIR" rev-parse HEAD)
git -C "$SOURCE_DIR" cat-file -e "$EXPECTED_CODE_SHA^{commit}"
if ! git -C "$SOURCE_DIR" merge-base --is-ancestor "$EXPECTED_CODE_SHA" "$ACTUAL_SHA"; then
  printf 'Approved code SHA %s is not an ancestor of checkout %s\n' "$EXPECTED_CODE_SHA" "$ACTUAL_SHA" >&2
  exit 1
fi
if [[ -n "$(git -C "$SOURCE_DIR" status --porcelain)" ]]; then
  printf 'Source checkout is not clean; refusing deployment.\n' >&2
  exit 1
fi
for payload in vpn-functions.sh vpn-tg-bot.sh tests/test_adguard_cli.sh; do
  if ! git -C "$SOURCE_DIR" diff --quiet "$EXPECTED_CODE_SHA" "$ACTUAL_SHA" -- "$payload"; then
    printf 'Deploy payload differs from approved code SHA: %s\n' "$payload" >&2
    exit 1
  fi
done
test -f "$SOURCE_DIR/vpn-functions.sh"
test -f "$SOURCE_DIR/vpn-tg-bot.sh"
```

Do not continue until F-12 (token rotation and argv fix) and F-14 (root-owned, non-writable production code and parent directories) are closed and reviewed. Do not copy the development checkout as-is if it fails these gates.

1. Получить commit SHA, прошедший review и необходимые checks. Проверить, что он содержит только ожидаемые изменения задачи 0.1: `vpn-functions.sh`, `vpn-tg-bot.sh` и fake CLI test.
2. Использовать подтверждённый `MAIN_SH_DIR=/usr/local/bin/vpngw` и проверить оба активных файла:

```bash
ACTIVE_DIR='/usr/local/bin/vpngw'
FUNCTIONS="$ACTIVE_DIR/vpn-functions.sh"
BOT="$ACTIVE_DIR/vpn-tg-bot.sh"
sudo test -f "$FUNCTIONS" && sudo test -f "$BOT"
sudo stat -c 'owner=%U group=%G mode=%a path=%n' "$FUNCTIONS" "$BOT"
sudo namei -l "$FUNCTIONS" "$BOT"
```

1. Штатно остановить только bot service: `sudo systemctl stop vpn-tg-bot.service`. Не останавливать `adguardvpn-starter`, routing scripts или VPN CLI daemon. Минутные cron-запуски starter продолжаются; reconnect action запрещён.
2. Создать backups обоих файлов и подготовить новые файлы рядом с ними (rename каждого файла остаётся на своей файловой системе):

```bash
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
FUNCTIONS_BACKUP="$FUNCTIONS.pre-0.1.$STAMP"
BOT_BACKUP="$BOT.pre-0.1.$STAMP"
FUNCTIONS_NEW="$FUNCTIONS.new.$STAMP"
BOT_NEW="$BOT.new.$STAMP"
sudo cp -a "$FUNCTIONS" "$FUNCTIONS_BACKUP"
sudo cp -a "$BOT" "$BOT_BACKUP"
sudo install -o root -g root -m 0755 \
  "$SOURCE_DIR/vpn-functions.sh" "$FUNCTIONS_NEW"
sudo install -o root -g root -m 0755 \
  "$SOURCE_DIR/vpn-tg-bot.sh" "$BOT_NEW"
sudo bash -n "$FUNCTIONS_NEW" && sudo bash -n "$BOT_NEW"
sudo mv -f "$FUNCTIONS_NEW" "$FUNCTIONS"
sudo mv -f "$BOT_NEW" "$BOT"
```

Если проверка нового файла не проходит, не запускать бот: восстановить оба backup и расследовать причину. Обновить функцию перед ботом; бот должен быть остановлен на время замены обоих файлов.

1. Запустить bot unit и проверить его статус/журнал:

```bash
sudo systemctl start vpn-tg-bot.service
sudo systemctl is-active vpn-tg-bot.service
sudo journalctl -u vpn-tg-bot.service --since '-5 minutes' --no-pager
```

Проверить, что основной VPN-интерфейс и forwarding работают. Не выводить process arguments: пока F-12 не закрыт, `systemctl status` может раскрыть token.

## Production smoke test

Негативные случаи (missing CLI и ненулевой exit code) проверяются fake CLI в тесте выше; намеренно ломать production `ADG_BIN` или подменять его на fake CLI нельзя.

Для задачи 0.1 production smoke ограничивается запуском бота без отправки команды `/set_*`, проверкой supervisor/logs и проверкой основного VPN/connectivity/client routing. **Не нажимать переключение локации на production:** в root crontab starter запускается каждую минуту и общий lock с ботом ещё не реализован. Реальный вызов проверяется fake CLI test; live integration test выполняется после задачи общего lock либо на отдельном тестовом узле. Успешный запуск бота не подтверждает корректность целевой страны; это покрывает задача 0.2.

## Rollback

Откатывать при ошибке старта бота, повторных ошибках `ADG_BIN`, неожиданном разрыве основного туннеля или ухудшении маршрутизации.

1. Штатно остановить только bot unit: `sudo systemctl stop vpn-tg-bot.service`.
2. Восстановить backup атомарной заменой в том же каталоге:

```bash
FUNCTIONS_ROLLBACK="$FUNCTIONS.rollback.$STAMP"
BOT_ROLLBACK="$BOT.rollback.$STAMP"
sudo cp -a "$FUNCTIONS_BACKUP" "$FUNCTIONS_ROLLBACK"
sudo cp -a "$BOT_BACKUP" "$BOT_ROLLBACK"
sudo mv -f "$FUNCTIONS_ROLLBACK" "$FUNCTIONS"
sudo mv -f "$BOT_ROLLBACK" "$BOT"
```

1. Запустить `vpn-tg-bot.service`, проверить `is-active`, journal без argv и проверить основной VPN/connectivity/client routing.
2. Не удалять backups до успешного наблюдения и завершения PR review; зафиксировать commit SHA, причину rollback и результаты диагностики.

Rollback этой задачи возвращает оба предыдущих файла (`vpn-functions.sh` и `vpn-tg-bot.sh`); он не меняет `/etc/vpn-gw.conf`, `/etc/msmtprc`, VPN-сессию намеренно или маршруты. Если восстановление не возвращает сеть, перейти к документированному recovery-процессу шлюза и не повторять deployment.

## Результат выполнения

Собрать автоматически доступные поля после deployment/checks:

```bash
sudo bash tools/collect-production-inventory.sh
```

В Markdown report будет секция `Runbook task 0.1: result fields` с source/production Git SHA, SHA-256 active bot/functions files и сравнением их с source, backup paths, fake CLI result, состоянием systemd/VPN interface/IPv4 forwarding и оператором/временем. Для доказательства installed payload требовать `Production payload matches source files: YES`; Git HEAD в production directory сам по себе этого не доказывает. Collector намеренно помечает production reconnect и rollback test как `NOT RUN`; заполнить их вручную только по фактическому журналу работ. Наличие backup файла не означает, что rollback был испытан.

- Approved source SHA / production repo HEAD: взять из report; проверить, что payload SHA-256 совпадает
- `vpn-functions.sh` backup path: взять из report; `NOT FOUND` требует выяснения
- `vpn-tg-bot.sh` backup path: взять из report; `NOT FOUND` требует выяснения
- Проверка fake CLI: взять из report; должна быть `PASS`
- Production smoke test / причина отложения: заполнить вручную; reconnect запрещён до снятия блокирующих рисков
- Health checks: взять статусы из report и вручную добавить фактический connectivity/client-routing test
- Rollback проверен/не требовался: заполнить вручную; collector не выполняет rollback
- Оператор и дата: взять из report и дополнить фактическим результатом работ

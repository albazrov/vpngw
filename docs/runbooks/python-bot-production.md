# Python Telegram bot: production runbook

This runbook describes the supported Python bot release. It assumes a new Python deployment; the legacy shell Telegram bot is not a supported runtime, migration target, or rollback option. Bash remains in use for VPN, routing, and recovery helpers.

## Runtime layout

| Component | Path / identity |
| --- | --- |
| systemd unit | `vpngw-bot.service` |
| Python entry point | `/home/pi/.venv/bin/python -m vpngw_bot` |
| Service user/group | `vpngw-bot:vpngw-bot` |
| Secret environment | `/etc/vpngw-bot.env` |
| Safe VPN config | `/etc/vpngw-bot.conf` |
| Static speed profiles | `/etc/vpngw-speed-tests.conf` |
| Writable state | `/var/lib/vpngw/bot_state.db`, `/var/lib/vpngw/bot_queue.db` |
| Root switch helper | `/usr/local/sbin/vpngw-root-switch` |
| Runtime state for root scripts | `/dev/shm/vpn_stats`, `root:root 0700` |

The Python process is unprivileged. Sudoers grants it only the root helper with `RO`, `DE`, or `FI`. The root helper verifies connectivity after switching; the bot must not be run as root.

## Fresh install and update

Prerequisites: the checkout is at `/home/pi/app/vpngw`, the venv exists at `/home/pi/.venv`, and dependencies from `python_bot/requirements.txt` are installed.

For a fresh install, create `/etc/vpngw-bot.env` with `TG_TOKEN` and `TG_ALLOWED_CHAT_IDS`; optional `TG_ADMIN_CHAT_IDS` must be a subset of allowed IDs. Do not put the token in command arguments, Git, or chat. Then run:

```bash
sudo /home/pi/app/vpngw/tools/pi-bot-deploy-commands.sh
```

The deploy script installs and enables the unit, helper scripts, sudoers rule, and `/etc/tmpfiles.d/vpngw.conf`; it applies the runtime directory rule, repairs existing SQLite ownership, and restarts the Python service. It preserves current allowed/admin chat IDs when rotating the token. It does not switch VPN location. `/etc/vpngw-bot.conf` is generated by deploy; do not make persistent local edits there. `/etc/vpngw-speed-tests.conf` is preserved if it already exists.

## Telegram operations

- `/start` or `/menu`: show the VPN menu.
- `/status`: show GeoIP city/country and speed.
- `/speed`: choose a configured speed-test endpoint.
- `/speedadd <id> <name> <https-url> <connect-timeout> <max-time>`: add a profile as an admin. Example: `/speedadd fast FastTest https://speed.example/test.bin 8 30`.

Custom endpoints must be direct HTTPS downloads on port 443, with no redirects or URL credentials. Their DNS answers must be public IPs and include at least one IPv4 address. Connect timeout is 1-60 seconds and maximum duration is 1-120 seconds. Profiles are stored in SQLite and become selectable immediately; measurements use the active VPN interface regardless of VPN destination.

## Health checks and logs

```bash
sudo systemctl is-active vpngw-bot.service
sudo systemctl status vpngw-bot.service --no-pager -l
sudo journalctl -u vpngw-bot.service -n 100 --no-pager
sudo journalctl -u vpngw-bot.service -f
sudo /opt/adguardvpn_cli/adguardvpn-cli status
sudo stat -c '%U:%G %a %n' /dev/shm/vpn_stats /var/lib/vpngw /var/lib/vpngw/bot_state.db /var/lib/vpngw/bot_queue.db
```

Expected: service active; runtime directory `root:root 700`; database files writable by `vpngw-bot`. For `sqlite3.OperationalError: attempt to write a readonly database`, check ownership/mode of both database files and `/var/lib/vpngw`, then rerun the deploy script. Do not delete the databases to clear the error.

The runtime directory is volatile and is recreated at boot by systemd-tmpfiles. Verify it after reboot with the `stat` command above. Never use mode `0777`.

## Verification

Local checks before release:

```bash
bash -n vpn-functions.sh
bash -n tools/vpngw-root-switch.sh
bash -n tools/pi-bot-deploy-commands.sh
python -m compileall -q vpngw_bot python_bot/tests
/home/pi/.venv/bin/python -m pytest -q python_bot/tests
bash tests/test_runtime_directory_permissions.sh
```

On the Pi, verify `/start`, `/status`, `/speed`, and an admin-only `/speedadd` using a known direct-download test endpoint. Do not treat a running process alone as proof that Telegram commands, speed measurement, or VPN switching work. Test VPN switching only when an interruption is acceptable; never run it as a routine health check.

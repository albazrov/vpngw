# План устранения проблем и развития Telegram-управления

План составлен по [реестру проблем](security-and-bug-findings.md) и статическому анализу исходников. Целевая архитектура гибридная: Bash сохраняется для коротких системных операций, а Telegram API, очередь и долговременное состояние постепенно переносятся в отдельный непривилегированный Python-сервис. Это поэтапная миграция, не полная перепись recovery/routing.

## Правила выполнения задач

- Каждая задача ниже рассчитана на отдельную небольшую feature/fix ветку от `dev` и отдельный PR в `dev`; не объединять независимые исправления.
- Следовать [процессу разработки, тестирования и выпуска](dev-to-test-pr-process.md) и [чек-листу после замечаний](developer-pr-fix-checklist.md): локальная работа на любом устройстве, PR в `dev`, затем `dev → test`, Docker test deployment на Raspberry Pi и только после отдельного sign-off PR `test → main`.
- Для изменённых shell-скриптов запускать `bash -n` и ShellCheck; добавить поведенческий тест или smoke-check для изменённого сценария. Не считать текущие placeholder unit/smoke/integration jobs реальными проверками.
- Агенту поручается только указанная задача: сохранить публичные интерфейсы, не менять несвязанные файлы, не добавлять произвольное выполнение shell-команд из Telegram и не сообщать об успехе без проверки результата.
- Перед изменением расписания или запуска на устройстве инвентаризировать действующую конфигурацию: `/etc/vpn-gw.conf`, cron, systemd, права и пути. Эти детали отсутствуют в репозитории.
- Dockerfile/Compose и deployment automation в репозитории пока отсутствуют. Не считать тестовую среду готовой, пока контейнерная изоляция от production routes/firewall не проверена на Raspberry Pi.
- Предварительная установка и настройка Docker описана в [руководстве для Raspberry Pi 4B](raspberry-pi-4b-docker-test-server-setup.md); сначала выполнить его инвентаризацию и stop checks, затем реализовывать задачи 5.3–5.5.
- Каждая задача, прежде чем считаться завершённой, получает task runbook в `docs/runbooks/<task-id>-<short-name>.md` с production deployment, тестом на успех/отказ, health checks, rollback и необходимыми согласованиями. Не придумывать deployment/service paths: неизвестные значения зафиксировать как precondition к инвентаризации.

Обозначения: `[ ]` не начато, `[x]` завершено, `[~]` отложено. В конце задачи записать PR/коммит и результат проверки.

## Definition of Done для каждого PR

- Изменение ограничено одной атомарной задачей и имеет тест успеха и отказа.
- Для задачи есть runbook с production deployment, test procedure, health checks, rollback и условиями безопасной остановки.
- Изменённые shell-файлы проходят `bash -n` и ShellCheck; поведенческие проверки пройдены.
- Изменённый Python service проходит unit/lint/type checks; зависимости закреплены и не требуют production secrets в тестах.
- Нет произвольного исполнения входа Telegram; права и подтверждения соответствуют матрице.
- CI завершился успешно, обязательные review comments закрыты; после новых коммитов validation и review выполнены повторно.
- PR прошёл установленный проектом путь `feature/fix → dev`, затем `dev → test`; прямые изменения в `test` не вносятся.
- Production rollout разрешён только после test deployment того же SHA, отдельного sign-off и проверенного rollback на staging; production deployment записан по SHA/image digest.

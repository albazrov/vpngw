# Процесс разработки, тестирования и выпуска: dev -> test -> main

## 1. Цель процесса

Данный документ описывает путь от локальной разработки до production для проекта `albazrov/vpngw`, где:

- локальная разработка ведётся на Raspberry Pi или другом компьютере в feature/fix-ветке, созданной от `dev`;
- после подготовки релиза создаётся PR `dev -> test`;
- после merge в `test` кандидат разворачивается на Raspberry Pi в отдельную тестовую директорию через Docker;
- после успешной проверки и отдельного review создаётся PR `test -> main`;
- production-версия размещается в `/usr/local/bin/vpngw/` с сохранением предыдущей стабильной версии для отката;
- в рамках PR выполняется автоматическая и ручная проверка кода и deployment-кандидата;
- замечания от ревьюеров и дополнительных агентов фиксируются в комментариях PR;
- разработчик обязан отработать замечания и отправить новый коммит в ту же ветку PR;
- после повторной проверки PR можно мержить в `test`.

---

## 2. Основные ветки

- `dev` — ветка разработки
- `test` — ветка проверенного кандидата для интеграционного тестирования на Raspberry Pi
- `main` — production-ветка; только протестированные и одобренные релизы
- `feature/*` или `fix/*` — рабочие ветки, созданные от `dev`

Рекомендуемое правило:

- изменения в `dev` проходят через feature/fix ветки;
- `test` обновляется только через PR из `dev`;
- `main` обновляется только через PR из `test` после успешного тестового развёртывания;
- прямые коммиты в `test` и `main` запрещены;
- PR в `dev`, `test` и `main` требует проверки и согласования;
- состояние ветки само по себе не означает, что соответствующая версия развёрнута на устройстве: deployment фиксируется отдельным commit SHA/tag.

---

## 3. Рекомендуемый lifecycle разработки

### 3.1. Создание задачи

- задача оформляется в issue или в проекте;
- разработчику назначается конкретный scope;
- фиксируется ожидаемый результат и критерии приемки.
- до начала реализации определяется, как безопасно проверить изменение, развернуть его на production и откатить. Для каждой завершённой задачи добавляется runbook в `docs/runbooks/<task-id>-<short-name>.md` либо соответствующий раздел в документации задачи.

### 3.2. Работа в feature branch

- создать ветку от `dev`:
  - `feature/<name>`
  - `fix/<name>`
- реализовать изменения небольшими атомарными коммитами;
- не смешивать разные по смыслу изменения в одном коммите;
- после готовности — отправить branch в GitHub.

### 3.3. Проверка до PR

Перед созданием PR разработчик должен:

- проверить bash-syntax для `.sh` файлов;
- прогнать shellcheck или эквивалентную валидацию;
- если изменён Python service: прогнать unit tests, lint и type checks, зафиксировать зависимости;
- при наличии smoke tests — прогнать их;
- проверить, что изменённый код соответствует требованиям проекта.

Разработчик может использовать Raspberry Pi или любой другой компьютер. Локальная рабочая копия — место разработки, а не тестовый/production сервер. Изменения попадают в `dev` через feature/fix PR, а не прямым коммитом.

---

## 4. PR flow: feature -> dev

После подготовки feature/fix branch:

1. создать PR в ветку `dev`;
2. запустить CI validation;
3. проверить, что все обязательные статусы зелёные;
4. получить review от одного или нескольких проверяющих;
5. исправить замечания и добавить новые коммиты;
6. повторить валидацию;
7. после зелёного статуса — merge в `dev`.

Это шаг гарантирует, что изменения стабилизированы до попадания в основной поток разработки.

---

## 5. PR flow: dev -> test

Когда изменения в `dev` готовы к проверке:

1. открыть PR `dev -> test`;
2. получить автоматическую проверку проекта через GitHub Actions;
3. при необходимости получить дополнительную верификацию от review agent'ов или проверяющих;
4. все замечания должны быть внесены в комментарии PR;
5. разработчик обязан их отработать и сделать новый commit в ту же ветку PR;
6. после повторной проверки PR разрешается merge в `test`.

Требование:

- PR нельзя считать готовым, пока не закрыты обязательные замечания;
- любые новые коммиты должны приводить к повторному запуску workflow и ревью.

---

## 6. Что должен делать разработчик при замечаниях в PR

При появлении comment'ов в PR:

1. открыть каждый комментарий;
2. понять, является ли он обязательным или рекомендацией;
3. внести правки в код;
4. сделать новый commit;
5. обновить PR;
6. дождаться повторной валидации;
7. подтвердить, что замечание закрыто.

Важно:

- не создавать новый PR вместо исправления текущего;
- не игнорировать комментарии, которые требуют исправлений;
- не мержить PR, пока review comments не закрыты.

---

## 7. Требования к проверке PR

PR считается готовым только если выполнены все условия:

- все обязательные workflow checks зелёные;
- shell scripts проходят `bash -n`;
- shell scripts проходят `shellcheck`;
- Python service проходит unit tests, lint/type checks; зависимости закреплены;
- integration tests используют fake Telegram API/CLI и не требуют production secrets или host routing;
- smoke-checks для критичных сценариев прошли;
- все замечания проверяющих закрыты;
- нет неисполненных комментариев по коду;
- изменения уже залиты в ту же ветку PR.
- добавлена инструкция конкретной задачи: prerequisities, backup/deploy, проверка успеха и отказа, health check, rollback и критерии остановки;
- если безопасный production test невозможен, runbook явно указывает ограничение, риск, необходимые согласования и безопасную альтернативу; рискованный тест не считается выполненным.

---

## 8. Проверка с помощью GitHub Actions

В репозитории есть `.github/workflows/pr-validation-extended.yml`, который сейчас запускается при PR в `dev` и `test`. Для полного процесса его нужно распространить на PR в `main`; placeholder unit/smoke/integration jobs должны быть заменены реальными тестами до использования зелёного CI как release gate.

Он автоматизирует базовую проверку:

- `bash -n` для всех `.sh` файлов;
- `shellcheck` для всех `.sh` файлов;
- целевые Python unit/lint/type checks должны быть добавлены вместе с Python service;
- smoke validation (сейчас placeholder);
- создание комментария в PR при неуспешной проверке.

Файл workflow:

- `.github/workflows/pr-validation-extended.yml`

## 9. Дополнительные review-agent'ы

Для более глубокой проверки в PR можно подключать:

- GitHub Copilot PR review;
- static analyzers;
- security bots;
- custom automation for architecture / stability review;
- human reviewers.

Их задача:

- проверять логику, а не только форматирование;
- находить риски по устойчивости и безопасности;
- проверять соответствие требованиям проекта;
- фиксировать замечания в комментариях PR.

Важный принцип:

- замечания дополнительного agent'а являются обязательными для оформления и отработки, если они помечены как blocking / required.

---

## 10. Рекомендуемые правила branch protection

Для `dev`, `test` и `main` следует включить:

- require pull request reviews before merging;
- require status checks to pass before merging;
- dismiss stale approvals when new commits are pushed;
- require conversation resolution before merge;
- require branches to be up to date before merging;
- disallow force push;
- block direct pushes to protected branches.

Для `main` дополнительно требовать одобрение владельца релиза и успешный deployment/test report для commit SHA, который входит в PR.

---

## 11. Минимальный процесс для команды

Ниже — стандартная схема:

1. Создать feature/fix branch от `dev`.
2. Реализовать изменения.
3. Запустить локальную проверку.
4. Создать PR в `dev`.
5. Дождаться CI и review.
6. Отработать замечания.
7. Снова сделать commit.
8. Повторить проверку.
9. Merge в `dev`.
10. Открыть PR `dev -> test`.
11. Запустить validation workflow.
12. Отработать замечания от агентов/ревьюеров.
13. Повторно прогнать проверку.
14. Merge в `test`.

Merge в `test` не означает автоматическое разрешение на production. Далее обязательны тестовое развёртывание на Raspberry Pi и отдельное принятие решения по процедуре ниже.

---

## 12. Ключевой принцип процесса

Проект должен жить в цикле:

- code -> validate -> review -> fix -> validate again -> merge

Это критично для проектного кода, где ошибки могут влиять на стабильность VPN-работы, маршрутизацию и диагностику.

---

## 13. Рекомендация по соблюдению процесса

Для команды желательно закрепить правило:

- “Нет merge без зелёного статуса PR.”
- “Нет merge без закрытых обязательных замечаний.”
- “Нет новых веток в `test` без PR.”
- “Любой новый коммит после review требует повторного прохождения валидации.”

---

## 14. Итог

Такой процесс создаёт дисциплину, которая помогает:

- сокращать количество скрытых ошибок;
- повышать качество кода;
- уменьшать риск регрессий в production-подобной среде;
- системно отрабатывать замечания агентов и ревьюеров;
- поддерживать code quality на уровне проекта.

## 15. Тестовый deployment и выпуск на Raspberry Pi

### 15.1 Подготовка Docker test environment

В репозитории пока нет Dockerfile/Compose; их нужно добавить отдельной задачей до первой выкладки в контейнер. Пошаговая предварительная настройка Pi описана в [руководстве Docker test-сервера](raspberry-pi-4b-docker-test-server-setup.md). Минимальная схема:

- отдельный образ с кодом одного конкретного commit SHA; тестовый код не монтируется в production-каталог;
- тестовая директория на Raspberry Pi, например `/srv/vpngw/test/<commit-sha>`, и отдельный Compose project/service;
- отдельная тестовая конфигурация и тестовые секреты; production `/etc/vpn-gw.conf`, auth state и рабочие данные не монтируются в тестовый контейнер;
- изоляция от host network и production routes/firewall; не монтировать Docker socket, не использовать `--privileged` и host PID;
- если тесту нужен TUN, выдавать только необходимое устройство/capability тестовому контейнеру. До включения проверить Docker bridge/firewall и состояние host `ip route`, `ip rule`, iptables/nftables до и после;
- для проверки VPN с реальными маршрутами сначала доказать, что тест не затрагивает основной tunnel. Если Docker на этом Raspberry Pi не обеспечивает требуемую изоляцию, использовать отдельный тестовый Raspberry Pi/VM.

Не использовать production VPN credentials в тестовой среде, если отдельный test account/тестовая авторизация не согласованы. Тестовый контейнер не должен автоматически менять локацию или перезапускать production-сервисы.

### 15.2 Поток от merge в test до решения о выпуске

1. Создать PR `dev -> test`; пройти CI, review и закрыть обязательные замечания.
2. После merge зафиксировать commit SHA. На Raspberry Pi получить именно этот SHA, развернуть в тестовую директорию и построить image с неизменяемым tag по SHA.
3. Выполнить unit/smoke/integration тесты; затем ограниченный runtime test: старт/остановка контейнера, healthcheck, Telegram/API mocks, fake CLI, восстановление после ошибки. Реальный VPN test запускать только в изоляции, доказанной в 15.1.
4. Сохранить commit SHA, image digest, конфигурацию без секретов, логи и результаты тестирования. При любой ошибке кандидат не продвигать; исправления снова проходят PR и тестовый цикл.
5. После согласования владельцем релиза открыть PR `test -> main`. В PR приложить тестовый отчёт, SHA/image digest и план отката. Ревьюер подтверждает, что на Raspberry Pi тестировался тот же commit SHA.
6. После merge в `main` выполнить production deployment по разделу 15.3. Не копировать напрямую произвольные файлы из рабочей директории.

### 15.3 Production deployment и rollback

- Хранить релизы versioned в `/usr/local/bin/vpngw/releases/<version-or-sha>/`; активный путь `current` переключать атомарно после предварительной проверки. Существующую схему `MAIN_SH_DIR`, cron/systemd и права сначала инвентаризировать и адаптировать к этому layout.
- До переключения проверить артефакт, свободное место, конфигурацию и доступность предыдущего релиза; сохранить manifest commit SHA/image digest и backup конфигурации без публикации секретов.
- Переключать версию под deployment lock. Выполнить post-deploy health checks: сервисы запущены, tunnel/connectivity и policy routing в ожидаемом состоянии, бот отвечает. Одного успешного старта процесса недостаточно.
- Если health check не проходит или заданный период наблюдения фиксирует регрессию, вернуть `current` на предыдущий релиз, перезапустить только необходимые сервисы, повторить health checks и отправить alert. Предыдущий стабильный релиз не удалять до завершения периода наблюдения.
- Откат приложения не должен автоматически менять/удалять пользовательские конфиги, базы или маршруты. Изменения формата состояния требуют отдельного совместимого/rollback плана.
- После rollout записать SHA, время deployment, health-check результаты и результат/причину rollback.

Критерии принятия в `main`: тестовый deployment прошёл для того же SHA; обязательный review закрыт; image/artifact воспроизводим; production rollback проверен на тестовой среде; назначен ответственный за окно deployment.

# Шаблон review-агента для PR

## 1. Название PR
- <не заполняется автоматически>

## 2. Объём изменений
- Кратко описать, что изменено:
- Список ключевых файлов:
- Тип изменения: feature / fix / refactor / docs / infra

## 3. Критерии проверки

### 3.1. Архитектура и стабильность
- [ ] Изменения не ломают текущую модель состояния и восстановления
- [ ] Нет прямого доступа к критическим системным действиям из UI/бота
- [ ] Состояние системы описано и проверяемо
- [ ] Нет скрытых глобальных состояний без проверки
- [ ] Обработаны таймауты и повторные попытки

### 3.2. Безопасность и доступ
- [ ] Команды доступны только авторизованным пользователям
- [ ] Нет неограниченного доступа к критическим операциям
- [ ] Нет необработанных инъекций или подстановок переменных без проверки

### 3.3. Каркас кода
- [ ] Функции имеют понятные возвращаемые статусы
- [ ] Ошибки обрабатываются явно
- [ ] Нет silent failure без записи события
- [ ] Есть логирование, где это критично

### 3.4. Тестирование
- [ ] Есть тесты для сценариев успеха
- [ ] Есть тесты для сценариев ошибки
- [ ] Есть проверка повторных запусков / idempotency
- [ ] Smoke tests покрывают критичный сценарий

## 4. Комментарии review-агента

### Блокирующее замечание
- Тип: blocking / major / minor / info
- Файл: <path>
- Строка / область: <line range>
- Проблема: <кратко>
- Почему это важно: <как влияет на стабильность/безопасность>
- Рекомендуемое исправление: <что сделать>
- Критерий закрытия: <как понять, что замечание исправлено>

### Пример записи
- Тип: blocking
- Файл: `vpn-tg-bot.sh`
- Область: обработка callback query и команд управления
- Проблема: команда выполняется напрямую без проверки статуса и очереди задач
- Почему важно: может вызвать повторный запуск операции и неконтролируемое состояние
- Рекомендуемое исправление: вынести действие в manager queue, добавить idempotency и статус task
- Критерий закрытия: бот отправляет задачу в очередь, а не вызывает команду напрямую

## 7. Принцип для agent review

Review-агент должен фиксировать не только “стиль”, но и:
- риск отказа;
- вопрос корректности переходов состояний;
- отсутствие тестов;
- несоответствие требованиям безопасности и управления;
- невозможность повторной проверки без конфликтов.

Если замечание не имеет понятного критерия проверки — оно не считается завершённым.

### F-11. Повторные подключения не ограничены между запусками стартера

- **Приоритет:** P1; фактическое число попыток зависит от расписания на устройстве.
- **Файл:** [adguardvpn-starter.sh](../adguardvpn-starter.sh)
- **Подтверждённое наблюдение:** `flock` исключает параллельные запуски, но следующий процесс может снова запустить recovery после выхода предыдущего. Очередь локаций конечна в каждом запуске, однако код проходит её ещё раз после обновления кэша. `current_try_count` только увеличивается/показывается и не ограничивает попытки; сбрасывается отчётом после успешной отправки email, а не при достижении лимита. В auth-ветке есть дополнительный вызов `connect` без `timeout`.
- **Риск:** при постоянном отказе VPN и частом расписании суммарные попытки растут без верхней границы, создавая лишнюю нагрузку на CLI/аккаунт и затрудняя диагностику. Тысячи попыток за конкретный интервал не подтверждены без crontab/systemd timer устройства.
- **Проверка исправления:** заданы лимит на цикл и общий cooldown/backoff между циклами; состояние попыток обновляется атомарно под lock; все вызовы `connect`, включая auth retry, ограничены timeout; успешная проверенная связь сбрасывает streak. Тест многократных запусков с fake CLI доказывает, что после лимита подключения приостанавливаются до cooldown/ручного разрешения.

### F-12. Telegram token раскрывается через process arguments

- **Приоритет:** P0; credential rotation требуется немедленно.
- **Основание:** в переданном оператором выводе `systemctl status` дочерний `curl` отображается с Telegram Bot API URL, содержащим token. В исходнике bot формирует такие URL в argv curl для polling и API requests.
- **Риск:** любой пользователь/инструмент, способный читать process command line или status/cgroup output, может получить полномочия Telegram-бота. Token также уже попал в переданное сообщение; считать его скомпрометированным.
- **Немедленное действие оператора:** отозвать старый token через BotFather; загрузить новый только в защищённую конфигурацию/credential store; не вставлять его в команды, PR, issue или runbook. После code fix перезапустить unit и проверить, что новое значение не видно в argv/status.
- **Исправление кода:** убрать секрет из command-line аргументов всех Telegram curl-вызовов (polling/send/answer callback); использовать API client/credential channel, не отражающий URL с token в process list. Простая ротация не устраняет повторное раскрытие.
- **Проверка закрытия:** `tests/test_telegram_token_argv.sh` проходит в CI; fake token отсутствует в curl argv и передаётся только через config FD; Telegram requests работают; secret отсутствует в logs/report; старый token отозван оператором.

## Архитектурный риск (не подтверждённая уязвимость)

### A-01. Shell используется для долгоживущего Telegram-бота и управления состоянием

- **Приоритет:** P2; поэтапное улучшение, без переписывания системных скриптов «одним релизом».
- **Основание:** Shell хорошо подходит для коротких вызовов системных утилит и существующих recovery-скриптов. В текущем `vpn-tg-bot.sh` в одном процессе объединены Telegram long polling, JSON-разбор, состояние offset, сетевые проверки и выполнение долгих системных операций.
- **Риск:** при росте количества команд, retries и конкурирующих задач сложнее гарантировать транзакционную обработку updates, тестировать ошибки/повторы и контролировать границу привилегий. Это архитектурный риск, а не доказательство, что язык Shell сам по себе небезопасен.
- **Целевое решение:** постепенно перенести Telegram API, аутентификацию пользователей, очередь и состояние задач в отдельный Python-сервис, работающий без root. Оставить Bash для существующих системных действий (VPN/recovery/routing), вызывая их через фиксированный контракт с валидированными аргументами и кодами результата. Привилегированные действия предоставить через узкий allowlist-интерфейс с проверкой на стороне привилегированного исполнителя; запрещён общий shell/command endpoint.
- **Проверка/критерий:** unit/integration tests покрывают update replay, idempotency, права, очередь и fake CLI; бот не работает от root; переданная строка не становится shell-командой; текущие системные скрипты сохраняют поведение; переход выполняется с тестовым периодом и возможностью возврата к предыдущему bot release.

### A-02. Секреты смешаны с путями и настройками в общей sourced-конфигурации

- **Приоритет:** P1 до инвентаризации; фактическая экспозиция зависит от владельца, mode и места хранения `/etc/vpn-gw.conf`.
- **Основание:** скрипты загружают `/etc/vpn-gw.conf` как shell-код через `source`. В частности, `vpn-tg-bot.sh` и `vpn-tg-send.sh` читают `TG_TOKEN` из общей конфигурации, где также используются `MAIN_SH_DIR` и другие операционные параметры/пути. Конфигурация SMTP отдельно указывает на `/etc/msmtprc`; его права и содержимое тоже требуют проверки.
- **Не подтверждено:** реальный список секретов в файлах на устройстве, наличие дубликатов, права/владелец, резервные копии и способ передачи конфигурации при deployment. Не считать, что токены уже утекли.
- **Риск:** при копировании/публикации config, избыточных правах или передаче всей конфигурации менее доверенному процессу могут раскрыться Telegram/SMTP credentials. `source` также означает, что любой, кто может менять файл, может выполнить произвольный shell-код при запуске скрипта. Пути сами по себе не являются секретами, но смешение затрудняет least-privilege и безопасный deployment.
- **Решение:** провести inventory и классификацию переменных; отделить несекретные пути/параметры от credentials. На переходном этапе использовать root-owned config с минимальными правами; для нового Python/systemd service предпочесть systemd credentials или отдельный credential file, доступный только конкретному service account. Не включать секреты в Git, образ, Compose manifest, отчёты или логи. Не менять формат `/etc/vpn-gw.conf`, пока не проверены все его consumers и расписание.
- **Проверка/критерий:** права config и `/etc/msmtprc` проверены на устройстве; каждый секрет доступен только требуемому сервису; config loader валидирует обязательные значения и не логирует их; тесты используют dummy secrets; rollback восстанавливает прежнюю конфигурацию без вывода секретов. Если credential уже публиковался, его нужно отдельно отозвать/ротировать.

## Требование развития (не дефект)

### R-01. Изолированная проверка приоритетной локации

- **Цель:** иметь настраиваемую приоритетную локацию для теста VPN-туннеля; значение задаётся конфигурацией и меняется авторизованной командой бота.
- **Ожидаемая изоляция:** тестовый туннель работает в отдельном сетевом пространстве, предпочтительно контейнере; он не переключает основной VPN и не изменяет host routes, policy rules, ipset или маршрутизацию основного трафика.
- **Ограничения:** Docker может менять host firewall; нужно подтвердить поведение на Raspberry Pi. Нельзя использовать host network, Docker socket и безусловный `--privileged`. Нужно проверить поддержку отдельного TUN и параллельной VPN-сессии/учётной записи провайдером. Если требуется гарантированное отсутствие любых host-side сетевых изменений, использовать отдельную VM/устройство вместо Docker.
- **Критерий готовности:** probe подключается к выбранной локации в изоляции, возвращает connectivity/фактическую страну/время проверки и завершается с очисткой; состояние основного VPN и маршрутизация до/после неизменны. Проверка не выполняет автоматическое переключение основного туннеля.

# План стабилизации и управления проектом vpngw

## 1. Контекст и итоговый анализ

Проект `albazrov/vpngw` представляет собой набор shell-скриптов для управления VPN-соединением AdGuard VPN на Raspberry Pi. Основная логика реализована в файлах:

- `adguardvpn-starter.sh` — основной цикл восстановления и проверки состояния;
- `vpn-functions.sh` — библиотека общих функций логирования, уведомлений и проверок;
- `vpn-tg-bot.sh` — Telegram-бот для управления и инспекции;
- `vpn-bypass-update.sh` — обновление маршрутов/обходов;
- `vpn-auth-helper.sh` — обработка сценариев авторизации;
- `vpn-loc-update.sh`, `vpn-log-sync.sh`, `vpn-email-send.sh` и др. — вспомогательные операции.

С точки зрения текущей архитектуры это рабочая, но хрупкая система, собранная из shell-сценариев с множеством файловых флагов, логов и побочных эффектов. Скрипты выполняют и бизнес-логику, и системную часть, и взаимодействие с Telegram, и операции восстановления.

Проблемы, обнаруженные при анализе:

1. Нет единого центра управления состоянием.
   - Состояние разбросано по флагам в `/dev/shm`, `STATS_DIR`, временным файлам и логам.
   - Флаги могут оставаться после аварии и приводить к ошибочным сценариям.

2. Нет строгого watchdog для сервисов.
   - Скрипты запускаются по cron/вручную, но нет явной схемы “процесс жив или умер”.
   - Если Telegram-бот завис, система может продолжать работать, но терять управление.

3. Сценарии плохо защищены от race conditions.
   - `inc_stat`, `check_state_change` и чтение/запись в файлы могут конфликтовать при параллельных запусках.

4. Условия восстановления и переключения завязаны на shell-проверки, без универсального статуса и очереди задач.
   - Логику восстановления сложно отлаживать и масштабировать.

5. Telegram-бот напрямую вызывает управленческие операции и внешние команды.
   - Это делает управление неидемпотентным и уязвимым к повторным командам, спаму и зависаниям.

6. Нет строгой схемы обработки ошибок и повторов.
   - Внешние HTTP- и CLI-вызовы имеют таймауты, но не унифицированы по контрактам ошибок.

7. Логика не разделена на ответственность.
   - Сервис проверки сети, бот управления, восстановление маршрутов, запуск VPN и уведомления смешаны.

В общем итоге проект зрелый как экспериментальный “операционный скрипт”, но не готов к устойчивой эксплуатации без дополнительного слоя управления и централизованного состояния.

## 2. Цель целевой архитектуры

Нужно перейти от “набор скриптов с флагами” к архитектуре, в которой:

- есть один управляющий процесс (manager daemon);
- есть одно актуальное состояние системы;
- команды идут через очередь задач и idempotency tokens;
- все критические действия выполняются только через manager;
- Telegram-бот является интерфейсом управления, а не прямым исполнителем;
- контроль исполнения и диагностика проходят через event log и health checks;
- изменения внедряются небольшими, безопасными шагами, без массового переписывания.

## 3. Целевая архитектура

### 3.1. Компоненты

1. `Manager Daemon` (Python)
   - Ядро системы.
   - Хранит состояние (`state.json` / SQLite).
   - Содержит очередь задач.
   - Выполняет команды управления.
   - Дергает `adguardvpn-cli`, `vpn-bypass-update.sh`, `vpn-auth-helper.sh` только через контролируемый слой.
   - Проверяет health, выполняет recovery и стабилизирует состояние.

2. `State Store`
   - Путь: `state/state.json` или SQLite.
   - Поля:
     - connection_state
     - vpn_if
     - net_if
     - current_location
     - last_good_location
     - auth_state
     - uptime
     - last_heartbeat
     - last_error
     - last_event_ts
     - command_history

3. `Event Log`
   - Краткие структурированные записи событий.
   - Типы событий:
     - startup
     - health_check
     - vpn_connected
     - vpn_dropped
     - auth_required
     - command_received
     - command_executed
     - command_failed
     - switch_attempt
     - switch_success
     - switch_failed

4. `Task Queue`
   - Команды на выполнение: `status`, `switch_location`, `reconnect`, `refresh_routes`, `check_health`.
   - Каждый task должен быть idempotent и иметь status: `queued | running | success | failed | timeout | canceled`.

5. `Telegram Adapter`
   - Отделяет Telegram API от системы управления.
   - Не вызывает действия напрямую.
   - Только отправляет команды в manager.
   - Только читает состояние и актуальные статусы.

6. `Watchdog / Supervisor`
   - Контролирует жизненный цикл процессов.
   - Наблюдает за работой manager, bot, monitor.
   - Перезапускает зависшие компоненты.
   - Для этого используется `systemd`/`supervisord`/`s6`.

7. `Command Gateway`
   - Явная точка входа для операций.
   - Управляет тем, кто может вызывать команды, логирует действия и утверждает их.

### 3.2. Требуемая архитектурная модель

Рекомендуемая архитектура:

- Основной исполнитель: Python 3.x
- Состояние: SQLite для устойчивости и простоты транзакций, либо JSON для небольших событий и простого доступа.
- Системный запуск: `systemd` unit files, restart policy
- Интерфейс управления: Telegram bot over HTTP
- Остальные shell-скрипты: остаются как адаптеры для запуска системных команд, но не как ядро логики

Почему именно так:

- shell плохо масштабируется для состояния и очередей;
- Python лучше работает с JSON/SQLite, HTTP, таймаутами и retries;
- `systemd` обеспечит стабильность процесса и автоматический restart;
- shell-скрипты можно оставить как “примитивы” для команд `curl`, `ping`, `adguardvpn-cli`, `iptables` и т. д.

## 4. Требования к разработке

Следующие требования обязательны для всех новых изменений:

### 4.1. Архитектурные требования

1. Единственный источник истины для состояния
   - Все компоненты читают только manager state.

2. Отделение интерфейса от исполнения
   - Telegram-бот не должен выполнять `adguardvpn-cli` напрямую.

3. Idempotency
   - Повторная команда не должна создавать двойное действие.
   - Для каждой команды нужен уникальный id.

4. Обязательный health check
   - Система должна проверять состояние сети и VPN регулярно и делать заметки в event log.

5. Graceful degradation
   - При ошибках внешних зависимостей система должна не падать, а переходить в безопасный режим.

6. Atomic state updates
   - Изменение состояния должно происходить атомарно.

7. Очередь задач вместо прямых вызовов
   - Команды проходят через `task queue`, а не выполняются по месту вызова.

8. Контролируемый доступ
   - Только авторизованные Telegram chat IDs могут управлять.

### 4.2. Требования к кодированию

1. Код должен быть без скрытых глобальных состояний, где это возможно.
2. Любое внешнее действие должно иметь явный результат и таймаут.
3. Логирование должно быть структурированным, а не просто echo в stdout.
4. Для диагностик должны сохраняться:
   - timestamp
   - component
   - event type
   - status
   - metadata
5. Все функции должны возвращать конкретный статус: `OK`, `ERROR`, `RETRY`, `AUTH_REQUIRED`, `FAILED`, `TIMED_OUT`.
6. Запрещено использовать неограниченное ожидание без watchdog.
7. Любая команда должна иметь понятный план fallback.

### 4.3. Требования к тестированию

1. Небольшие изменения
   - Изменения вносятся маленькими PR, чтобы было легче ревью и откат.

2. Unit tests для критичных функций
   - парсинг состояния,
   - проверка health,
   - обработка ответов API,
   - фильтрация команды,
   - retry logic,
   - idempotency logic.

3. Integration tests
   - симуляция `adguardvpn-cli` через fake executable,
   - проверка обработки ответов и статусов,
   - проверка сценариев `auth_required`, `switch_success`, `switch_failed`.

4. Smoke tests
   - запуск manager daemon в controlled environment,
   - проверка startup/shutdown/restart,
   - проверка event log/heartbeat.

5. Regression tests
   - каждый фикс для восстановления должен иметь тест воспроизведения проблемы.

6. Тесты должны проверять не только “успех”, но и “ошибки и восстановление”.

### 4.4. Требования к внедрению

1. Внедрение поэтапное.
   - Нет “big bang rewrite”.

2. Сначала добавляем наблюдаемость.
   - Сбор state, event log, health metrics.

3. Затем выделяем manager.
   - Временно shell-скрипты вызывают manager, а не наоборот.

4. Затем отделяем бота от прямых действий.
   - Bot → queue command → manager → executor.

5. Только после этого удаляем устаревшие паттерны.
   - Оставляем совместимость с существующими shell-примитивами минимум на 1 релиз.

6. Каждая стадия должна иметь:
   - описание изменений,
   - тест-кейсы,
   - rollback plan.

## 5. Этапы внедрения

### Этап 0. Наблюдаемость и диагностика

Цель: не менять поведение, но сделать систему прозрачной.

Задачи для агентов:
- добавить структурированный event log;
- написать helper для heartbeat и last_seen;
- перевести `log_message` в формат JSON/structured log;
- добавить `state` snapshot с текущим health;
- добавить стабильный таймер для `check_internet` и `check_geo`;
- зафиксировать все ключевые статусы: `connected`, `degraded`, `auth_required`, `recovery`, `failed`.

Результат:
- система начинает документировать фактическое состояние без изменения бизнес-логики.

Требования:
- Обязательная совместимость со старым shell-кодом.
- Без изменения CLI интерфейса.

---

### Этап 1. Единственный state manager

Цель: убрать разрозненное состояние.

Задачи для агентов:
- создать `state_manager.py`;
- реализовать `load_state()`, `save_state()`, `update_state()`, `read_event_log()`;
- мигрировать флаги `AUTH_FLAG`, `last_temp`, `last_vpn_state` в общую state-структуру;
- добавить `flock`-блокировки на запись;
- добавить TTL/validation для stale flags;
- синхронизировать `check_state_change` с manager state.

Результат:
- все компоненты работают через единый state store;
- stale flags больше не мешают системе.

Требования:
- no big rewrite;
- желательно оставить старые файлы как fallback на 1–2 релиза.

---

### Этап 2. Выделение manager daemon

Цель: вынести логику управления из shell в отдельный процесс.

Задачи для агентов:
- создать `vpn_manager.py`;
- добавить `health_check_loop()`;
- добавить `recovery_loop()`;
- добавить `task_queue` и `task_executor`;
- реализовать `switch_location(location)`;
- реализовать `reconnect()`;
- реализовать `status()`;
- добавить `last_error`, `current_operation`, `task_results`.

Результат:
- управление происходит через manager, а не напрямую из shell-команд.

Требования:
- при старте manager должен понять текущее состояние;
- все операции должны быть логируемы и идемпотентны;
- если CLI не отвечает, task должен идти в `failed`/`timeout` статус.

---

### Этап 3. Отделение Telegram-бота от прямых действий

Цель: сделать бота интерфейсом, а не исполнителем.

Задачи для агентов:
- создать новый `telegram_adapter.py`;
- бот отправляет команды в manager через IPC/API;
- удалить из `vpn-tg-bot.sh` прямой вызов `adguardvpn-cli`;
- добавить авторизацию по `TG_CHAT_ID` и whitelist;
- добавить rate limit и cooldown для команд;
- добавить callback confirm для критических команд.

Результат:
- бот только отправляет команды и отображает состояние.

Требования:
- никакой команды `connect` из бота без подтверждения task-id;
- повторная команда не должна дублировать действие.

---

### Этап 4. Watchdog и systemd

Цель: сделать процессы устойчивыми к сбоям.

Задачи для агентов:
- создать `systemd` unit для `vpn-manager`, `vpn-bot`, `vpn-monitor`;
- добавить `Restart=always`, `RestartSec=10`;
- реализовать heartbeat file / PID file;
- реализовать supervisor для process liveness;
- обеспечить graceful shutdown.

Результат:
- процессы автоматически восстанавливаются после зависания.

Требования:
- один контейнер/служба = один ответственный процесс;
- зависание процесса не должно приводить к рассинхронизации состояния.

---

### Этап 5. Добавление retry policy и safe fallbacks

Цель: уменьшить нестабильность network/CLI вызовов.

Задачи для агентов:
- добавить `RetryPolicy` для HTTP и CLI вызовов;
- добавить `timeout`, `backoff`, `max_retries`;
- добавить fallback для `ip-api.com` и других geolocation providers;
- добавить handling для `AUTH_REQUIRED` и `account login` scenarios;
- реализовать “safe fallback mode” при отсутствии VPN-данных.

Результат:
- система не “пропадает” на каждом таймауте.

Требования:
- Повторные попытки только для идемпотентных операций.
- Операции с изменением состояния должны быть явно отслеживаемыми.

---

### Этап 6. Тестирование и hardening

Цель: сделать проект пригодным для продолжительной эксплуатации.

Задачи для агентов:
- написать unit tests для health logic;
- добавить fake shell executables для adguardcli;
- добавить integration tests для recovery flow;
- добавить smoke tests для manager start/stop;
- добавить regression tests для past failures.

Результат:
- минимальный уровень уверенности в корректности повышен.

Требования:
- нового кода должно быть меньше, чем изменения в старых файлах;
- каждый релиз должен иметь проверку smoke-tests.

## 7. Рекомендуемая реализация при разработке

### Технология

- Python 3.11+ для manager и adapter
- SQLite для state
- JSONL или SQLite для event log
- `systemd` для process supervision
- shell-скрипты остаются только как thin wrappers вокруг внешних системных двоичных команд

### Почему эта архитектура лучше текущей

- легче отлаживать;
- меньше скрытых зависимостей;
- проще тестировать;
- проще реализовать retry и backoff;
- безопаснее в эксплуатации;
- лучше совместимо с ботом и cron.

## 8. Практическая стратегия внедрения без риска

1. Не переписывать все в одном PR.
2. Сначала ввести observability.
3. Потом вынести state.
4. Потом вынести manager.
5. Потом отключить прямые вызовы из бота.
6. Потом заменить shell-сценарии на контролируемые adapters.
7. Потом удалить legacy code после стабилизации.

Это важно, потому что проект уже выполняет важные функции на реальном оборудовании. Любой “большой рефакторинг” без промежуточных шагов создаст риск простоя VPN/обходов.

---

## 9. Критерии принятия решения о готовности проекта после изменений

Проект можно считать готовым для стабильной эксплуатации, если соблюдены все условия:

- Manager стабильно работает без зависаний;
- health checks выполняются регулярно;
- бот не вызывает прямые системные команды;
- состояние хранится в одном месте;
- event log фиксирует все важные изменения;
- каждый critical action имеет retry и fallback;
- все сценарии покрыты smoke/integration tests;
- есть clear rollback plan и service monitoring.

## 10. Краткий итог

Текущий проект — это сильный прототип “самоуправляемого VPN-шлюза”, но требуются архитектурные разделение ответственности, единственный state, watchdog, безопасный Telegram interface и тестируемая очередь задач. Наиболее правильный путь — не переписывать всё с нуля, а внедрять стабильность постепенно, небольшими изменениями, с обязательным тестированием и наблюдаемостью.

Это даст проекту:
- стабильность,
- предсказуемость,
- удобное управление через бота,
- простую диагностику аварий,
- безопасный путь к дальнейшему развитию.

## 12. Обязательные требования для реализации следующего цикла

- реализовывать на Python 3.11+
- использовать SQLite или JSON state store
- разделить shell-скрипты и manager layer
- не удалять legacy shell scripts сразу
- писать unit/integration/smoke tests
- внедрение делать маленькими incrementally-коммитами
- каждое изменение должно быть проверяемо по rollback plan
- Telegram-бот должен стать adapter, а не executor
- все критические операции должны иметь task ID, retry, timeout, log
- health checks + watchdog обязательны

Эти требования должны быть зафиксированы в любом PR, который будет начинать архитектурную проработку.


## 13. Рекомендация по первому шагу

Первые три задачи в порядке приоритета:

1. Добавить state + event logging.
2. Создать manager daemon skeleton.
3. Перевести Telegram-бот на командную очередь вместо прямого вызова действий.

После этого можно безопасно перейти к watchdog/systemd и тестам.
